* Proposal :idea:
** Title / Mandatory
#+begin_quote
Short and precise title.
#+end_quote
Simplistic dynamic TrustZone for ARMv9 Realm Management Extension
** Abstract/scene problem / Mandatory
#+begin_
General problem that is happened in real life in real applications.
#+end_quote
TrustZone is a well-established extension for ARM-A processors used
commonly in mobile phones and it is used for security-critical operations.
Generally, it utilizes the security approach when the primary
operating system is always considered as actually compromized,
leaving important data processing to a processor state that is completely
separated from the primary (rich) operating system by memory and processor state
on a hardware level.
It proves its strong advantages in real life applications such as DRM,
biometric data processing, authorization management etc.
However, this technology is usually tightly coupled to the Vendor OS,
and any general 3rd party developer cannot simply write a new application
that may utilize the advantages of such separate compute state.
We propose to utilize the novel ARMv9 extension RME (Realm Management Extension)
to construct a dynamic secure programming environment that allows
an utilization of hardware secure-non-secure memory isolation
and other techiques for better security of the whole ecosystem -- for HongMeng
particularly.
** Scenario problem / Mandatory
#+begin_quote
Simple use-case scenario.
#+end_quote
In this scenario, 3rd party developers refers to any developer
besides the system developer of HongMeng itself.
It may be either enternal Huawei entity of some external corporate
and/or individual entity.

We will provide the following problem as a large case.
3rd party developers wants to improve security of its application,
this may be a banking application, custom ML & biometrics application
including custom fingerprint and voice recognition app.
Also, a custom DRM including some non-standard extension, or multiple DRMs that operate
at the same time.
This may be a dynamically customizable video & audio pipelines that must be
done securely to avoid raw data leakage and that shows on some secure device
(secure frame buffer, secure audio output).
It may be also a gama developer who would like to provide a robust
anti-cheat engine for mobile online game securing application memory
in separate state.
It may be also a separate banking application and/or payment system
that requires an authorization using secure intput device.
It may be also a 3rd party medical application that accesses and processes
sensitive user data.
This may be also a 3rd party corporate service including private chat,
document management system, approval management system, etc.
All of these applications are generaly within domain of a "classic" TrustZone
for mobile phones, but it is hard for external developer to enter this domain
-- it must either sign a special agreement with Vendor, and it is hardly possible
in practice due to law regulations and technical complexities -- like, all
Trusted Applications must be signed with Vendor's key, and they usually work within
the common Trusted OS infrastructure, with the possible access to Vendor's
proprietary technologies and devices.
We propose to actually allow more broad developer audience to develop
their security-critical application for Huawei devices.
** Program description (?)
#+begin_quote
Short one sentence that fully describes the whole idea.
#+end_quote
Utilize the dynamic nature of ARMv9 Realms to allow a TrustZone-like execution environment
for general developers for Huawei consumer & corporate devices.
** Solution description / Mandatory
#+begin_quote
Step-by-step description of how to fix the example scenario.
#+end_quote
We will allow utilization of dynamic TrustZone using the following approach.
ARMv9 provides a new set of computing state that provided separated execution
environments with different privilege levels:
1. Root state on with exception level 3 only;
2. Normal World with exception levels 0..2, usualy a place for
   hypervisor, rich operating system and virtual machines.
   A common example is HongMeng with hmvirt hypervisor and several
   guest VMs.
3. Secure World with exception levels 0..2 that consists of
   secure partition manager, trusted OS that run trusted applications,
   and potentially a set of separate secure firmwares that may be used
   to control some vendor-specific secure devices.
4. Realm World -- a mutuably independent with the Secure World
   processor state with exception levels 0..2. It usually
   requires a realm management minitor (a simple hypervisor)
   and a set of Realm virtual machines.

ARM specifically designed Realms in such a way to allow a dynamic
provision of Realm VMs in terms of memory, interrupt handling and scheduling.
All Realms are constructed from memory pages supplied by Normal World.
After initial provisionning, Normal World does not have an access to that pages,
it can only manage them.
Normal World also provides scheduling so, generally speaking, Realms does not
provide an _availability_ gurantee, only _confidentiality_ and _integrity_,
but for most applications it is sufficient.

We propose to create a framework for Realm management that consists of the following parts:
1. A HongMeng userspace and kernel infrastructure that allows the population of Realms,
   as well as needed support in hmvirt and/or hmpart.
2. A completely new entity `hmrmm` (Hong Meng Realm Management Monitor) -- a hypervisor-like
   entity that runs in Realms' EL2 and provides basic message passing and Realm VM isolation,
   as well as Realm attestation.
3. A framewok that allows a 3rd party developer to actually develop applications
   that work within a Realm.

One of serious problems of current TrustZone technology is the utilization
of highly specialized API, e.g. Global Platform API, that provide
abstractions for coommunication between worlds. We propose not to use it at all,
but let develoeprs write their own programs as for a native system in Normal World,
but allowing to offload some *functions* and *data* _whitin the same program_
to a different execution state.

From develoeprs' point of view it may look like some specific annotation for
functions and data structures with normal ABI, that a ensured by runtime
to be executed in a Realm World. Other functions may simply call such
annotated functions during the execution in a Normal World, but instead of simple
call, this call will translate into interworld communication request and is processed
inside a copy of a program in the Realm World.
Runtime must ensure that some set of functions (a Realm internal API)
is only available within the annotated
functions -- an attempt to call a external API provided by this Realm framework within
not-annotated function will result either in compile or in run time error.
Compile time check withh require a modification of a compiler, however
it is possible to provide simple runtime checks.
This Realm internal API may present some features that may be useful for secure computing,
such as trusted storage, key derivation, authentification mechanisms,
trusted devices and trusted user interface, together with the general
HongMeng and/or POSIX API.
It might be also possible to create a shared memory buffer that is used to pass
large data between worlds.

From runtime point of view, the 3rd party application that requests some
computation in Realms World, is represented as an ELF file with several
new loadable segments. it must contain a usual loadable segments for .text,
.data, .bss and relocation tables, and it also must contain a separate set
of loadable segments for .text, .data and .bss as well as relocation
tables that are run in the Realm world.
Upon load, these special segments are used to construct a new isolated Realm VM
together with some interface libraries that a load from some page cache.
It also substitues direct references from normal code to realm code with
the calls of RPC-like interfaces of Realm interface library, doing
the same thing in the Realm counterpart.
Secure services that are available from Realm VM are provided by a vendor Realm VM
and/or by vendor's Trusted OS.

After the load, the usual execution starts from a main C entry point.
Eventually, program reaches the call to some function that is put in the
Realm VM. It normally calls such a function, but execution passes to the
interface function within the interface library that marshals all of
the function arguments into some format, and passes it via the SMC mechanism
to the HongMeng Realm Management Monitor. It processes this request
and passes it to he appropriate Realm VM. An alternative to this process
may be an utilization of shared non-secure memoty between a Normal World
and Realm VM. Ultimately, this call reaches the implementation of the
needed function in the Real VM, where it processes important data
using the other functions written by developer, as well as colling
of some external secure API, operation with some new capabilities
and/or POSIX-like driver interfaces that are not available from the Normal World
-- trusted user interface and trusted storage may be among these examples.

After processing the originally called function normally returns, this return
translates to a marshalled SMC request to the Normal World (or some shared memory operation),
and finally execution control returns to the main part of an application.
